# Modules-only Builds Architecture

## Обзор

Начиная с версии 1.0.10, Yapay SDK использует архитектуру modules-only builds с shared module cache для обеспечения ABI совместимости между сервером и плагинами.

## Принципы архитектуры

### 1. Единый модульный кеш
- Все сборки (сервер и плагины) используют единый кеш модулей `/gomodcache`
- Это гарантирует, что все компоненты используют одинаковые версии зависимостей
- Исключает конфликты версий между сервером и плагинами

### 2. Отдельные go.mod для плагинов
Каждый плагин имеет собственный `go.mod` файл:

```go
module my-plugin

go 1.24.0
toolchain go1.24.7

require (
    github.com/metalmon/yapay-sdk v1.0.10
    github.com/sirupsen/logrus v1.9.3
)

// Replace директива для синхронизации версии golang.org/x/sys
replace golang.org/x/sys => golang.org/x/sys v0.36.0

require golang.org/x/sys v0.36.0 // indirect
```

### 3. Replace директивы для синхронизации
Используются `replace` директивы для принудительной синхронизации версий общих зависимостей:

```go
replace golang.org/x/sys => golang.org/x/sys v0.36.0
```

Это гарантирует, что все плагины используют ту же версию `golang.org/x/sys`, что и сервер.

## Конфигурация сборки

### Переменные окружения
```bash
# Для сборки приложений и плагинов
GOMODCACHE=/gomodcache
GOCACHE=/tmp/gocache

# Для инструментов разработки (lint, fmt)
LOCAL_GOMODCACHE=$(HOME)/.cache/go/mod
LOCAL_GOCACHE=$(HOME)/.cache/go-build
```

### Docker Builder
Builder образ содержит предзагруженный модульный кеш:

```dockerfile
FROM golang:1.24-alpine AS builder

# Устанавливаем кеш модулей
ENV GOMODCACHE=/gomodcache
ENV GOCACHE=/tmp/gocache

# Создаем директорию кеша
RUN mkdir -p /gomodcache && chmod 777 /gomodcache

# Загружаем все модули
RUN go mod download all
```

## Конфигурация плагинов

### Автоматическая загрузка
Сервер автоматически обнаруживает и загружает плагины:

1. **Сканирование директории** `plugins/` на наличие `.so` файлов
2. **Загрузка конфигурации** из `plugins/{plugin-name}/config.yaml`
3. **Валидация** обязательных полей конфигурации
4. **Регистрация** плагина в системе

### Структура директории плагина
```
plugins/my-plugin/
├── my-plugin.so        # Скомпилированный плагин
└── config.yaml         # Конфигурация плагина
```

### Обязательные поля конфигурации
```yaml
name: "My Plugin"           # Название плагина
domain: "example.com"       # Домен клиента
enabled: true               # Включен ли плагин
yandex:
  merchant_id: "YOUR_ID"    # ID мерчанта Яндекс.Пей (используется как client ID)
  secret_key: "YOUR_KEY"    # Секретный ключ
security:
  request_enforcement: monitor  # Политика валидации
  rate_limit: 1000            # Лимит запросов
  cors:
    origins: ["https://example.com"]  # CORS домены
plugin:
  type: "so"                # Обязательно для .so плагинов: тип плагина ("builtin", "so", "grpc")
  path: "my-plugin.so"      # Обязательно для .so плагинов: путь до .so файла
```

**Важно:** 
- Поле `id` в конфигурации плагина игнорируется сервером. В качестве идентификатора клиента всегда используется `yandex.merchant_id`
- По умолчанию используется тип плагина `builtin`. Для SDK плагинов с кастомной логикой **обязательно** указать `plugin.type: "so"` и `plugin.path`

## Преимущества архитектуры

### 1. ABI совместимость
- Сервер и плагины используют одинаковые версии зависимостей
- Исключены конфликты версий и runtime ошибки
- Плагины могут безопасно использовать типы из общих зависимостей

### 2. Детерминированная сборка
- Все сборки используют одинаковые версии зависимостей
- Результат сборки не зависит от локального окружения разработчика
- Воспроизводимые сборки в CI/CD

### 3. Производительность
- Модульный кеш предзагружается в builder образе
- Никаких загрузок зависимостей во время сборки плагинов
- Быстрая сборка плагинов

### 4. Изоляция
- Каждый плагин имеет собственную конфигурацию модулей
- Изменения в одном плагине не влияют на другие
- Простота добавления новых плагинов

## Миграция с vendor-based сборки

### Что изменилось
1. **Удален vendor/** - больше не используется
2. **Добавлены go.mod** - каждый плагин имеет свой файл
3. **Replace директивы** - для синхронизации версий
4. **Shared module cache** - единый кеш для всех сборок

### Совместимость
- Все существующие плагины продолжают работать
- API плагинов не изменился
- Конфигурация сервера дополнена новыми полями

## Проверка совместимости

### Команда проверки
```bash
make check-compatibility
```

### Что проверяется
1. Сборка плагинов без загрузки зависимостей
2. Существование и валидность .so файлов
3. Консистентность версий зависимостей
4. Отсутствие vendor директорий
5. ABI совместимость

## Лучшие практики

### 1. Версионирование зависимостей
- Всегда используйте `replace` директивы для общих зависимостей
- Синхронизируйте версии с сервером
- Обновляйте версии SDK через `versions.env`

### 2. Структура плагина
```
src/my-plugin/
├── go.mod              # Модульная конфигурация
├── go.sum              # Хеши зависимостей
├── main.go             # Код плагина
├── config.yaml         # Конфигурация плагина
└── README.md           # Документация плагина
```

### 3. Сборка плагинов
```bash
# Всегда используйте официальный builder
make build-plugin-my-plugin

# Проверяйте совместимость
make check-compatibility
```

### 4. Тестирование
```bash
# Тестируйте плагины
make test-plugins

# Проверяйте совместимость
make check-compatibility
```

## Устранение проблем

### Ошибки совместимости
```bash
# Проверьте версии зависимостей
make check-compatibility

# Обновите go.mod плагина
go mod tidy

# Пересоберите плагин
make build-plugin-my-plugin
```

### Конфликты версий
1. Проверьте `replace` директивы в go.mod
2. Убедитесь в синхронизации с сервером
3. Используйте `versions.env` для контроля версий

### Проблемы сборки
1. Проверьте доступность builder образа
2. Убедитесь в правильности go.mod
3. Проверьте права доступа к кешу модулей

---

**Важно**: Всегда используйте официальный builder образ для сборки плагинов в production!
